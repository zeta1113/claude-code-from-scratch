# Agent Team Design Patterns

## 실행 모드: 에이전트 팀 vs 서브 에이전트

### 에이전트 팀 (기본 모드)

팀 리더가 팀원들을 조직하고, 팀원들은 독립적 Claude 인스턴스로 실행.

- 팀원들이 `SendMessage`로 직접 통신
- `TaskCreate/TaskUpdate`로 공유 작업 관리
- 직접 대화, 도전, 검증 가능
- 리더를 거치지 않은 정보 교환

**제약:**
- 세션당 한 팀만 활성화
- 중첩 팀 불가
- 토큰 비용 높음

### 서브 에이전트 (경량 모드)

메인 에이전트가 `Agent` 도구로 서브 에이전트 생성.

- 결과를 메인에게만 반환
- 서로 통신 불가
- 가볍고 빠름, 토큰 효율적

**제약:**
- 에이전트 간 통신 불가
- 메인이 모든 조율 담당

### 선택 의사결정

```
에이전트가 2명 이상인가?
  ├─ YES: 상호 통신이 필요한가?
  │     ├─ YES → 에이전트 팀 모드 (기본)
  │     └─ NO  → 서브 에이전트 가능
  └─ NO: 단일 에이전트 또는 스킬만으로 충분
```

## 아키텍처 패턴 6가지

### 1. Pipeline — 순차 작업

이전 단계 출력이 다음 단계 입력이 되는 선형 흐름.

**예:** 소설 집필 (세계관 → 캐릭터 → 플롯 → 집필 → 편집)

**주의:** 병목이 전체 지연 초래. 중간 단계 실패 시 전체 재실행 필요.

### 2. Fan-out/Fan-in — 병렬 처리 후 통합

동일 입력을 여러 에이전트가 독립적으로 처리 후 결과 통합.

**예:** 종합 리서치 (공식/미디어/커뮤니티/배경 동시 조사 → 통합)

**팀 모드 필수:** 팀원들이 발견을 공유하고 실시간 조사 방향 수정 → 품질 향상.

### 3. Expert Pool — 조건부 전문가 호출

상황에 따라 적절한 전문가를 선택적으로 호출.

**예:** 코드 리뷰 (보안/성능/아키텍처 전문가 선택 호출)

**서브 에이전트 적합:** 필요한 전문가만 호출, 통신 오버헤드 불필요.

### 4. Producer-Reviewer — 생성 후 검증

생성 에이전트와 검증 에이전트가 쌍으로 동작.

**예:** 웹툰 (artist 생성 → reviewer 검수 → 재생성, 최대 2-3회)

**팀 모드 유용:** 실시간 피드백 교환으로 품질 향상.

**주의:** 재시도 2~3회로 제한. 무한 루프 방지.

### 5. Supervisor — 동적 작업 분배

중앙 에이전트가 전체 상황을 보면서 동적으로 작업 배분.

**예:** 대규모 코드 마이그레이션 (감독자가 파일 분석 후 워커 배치)

**팀 모드 적합:** 공유 작업 목록이 자체 요청(claim) 패턴과 자연스럽게 매칭.

**Fan-out과 차이:** 작업이 사전 고정이 아닌 런타임에 동적으로 할당됨.

### 6. Hierarchical Delegation — 계층적 위임

총괄 → 팀장 → 실무자의 재귀적 위임.

**예:** 풀스택 앱 (총괄 → 프론트팀장/백팀장 → 실무자)

**주의:**
- 깊이 2단계 이내 권장 (지연·컨텍스트 손실)
- 팀 모드 중첩 불가 → 1단계만 팀, 2단계는 서브 에이전트

## 복합 패턴

| 패턴 조합 | 구성 | 예시 |
|---------|------|------|
| 팬아웃 + 생성-검증 | 병렬 생성 후 각각 검증 | 다국어 번역 (4개 언어 병렬 → 각 네이티브 리뷰) |
| 파이프라인 + 팬아웃 | 순차 일부 병렬화 | 분석(순차) → 구현(병렬) → 통합 테스트(순차) |
| 감독자 + 전문가 풀 | 감독자가 전문가 동적 호출 | 고객 문의 처리 (분류 → 적합 전문가 할당) |

**원칙:** 모든 복합 패턴은 에이전트 팀 사용. 팀원 간 활발한 커뮤니케이션이 결과 품질의 핵심.

## 에이전트 타입 선택

### 빌트인 타입

| 타입 | 용도 |
|------|------|
| `general-purpose` | 전체 도구 접근 (웹 조사, 범용 작업) |
| `Explore` | 읽기 전용 (코드베이스 탐색, 분석) |
| `Plan` | 읽기 전용 (아키텍처 설계, 계획) |

### 커스텀 타입

`.claude/agents/{name}.md`에 정의 후 `subagent_type: "{name}"`으로 호출.

**선택 기준:**

| 상황 | 타입 |
|------|------|
| 역할이 복잡하고 재사용 | 커스텀 타입 |
| 조사/수집만 필요 | `general-purpose` + 상세 프롬프트 |
| 코드 읽기만 필요 | `Explore` |
| 설계/계획만 | `Plan` |
| 파일 수정 필요 | 커스텀 타입 |

**원칙:** 모든 에이전트는 `.claude/agents/{name}.md`로 정의. 모든 에이전트는 `model: "opus"` 사용.

## 에이전트 정의 구조

```markdown
---
name: agent-name
description: "1-2문장 역할"
model: opus
---

# Agent Name

당신은 [도메인]의 [역할] 전문가입니다.

## 핵심 역할

## 작업 원칙

## 입력/출력 프로토콜

## 팀 통신 프로토콜 (팀 모드인 경우)
- SendMessage 발신 대상과 내용
- 수신 메시지 처리 방법

## 에러 핸들링

## 협업
```

## 에이전트 분리 기준

| 기준 | 분리 | 통합 |
|------|------|------|
| 전문성 | 영역이 다르면 분리 | 영역이 겹치면 통합 |
| 병렬성 | 독립 실행 가능하면 분리 | 순차 종속이면 통합 고려 |
| 컨텍스트 | 부담이 크면 분리 | 가볍고 빠르면 통합 |
| 재사용성 | 다른 팀에서도 쓰면 분리 | 이 팀에서만 쓰면 통합 고려 |

## 스킬 vs 에이전트 구분

| 구분 | 스킬 | 에이전트 |
|------|------|---------|
| 정의 | 절차적 지식 + 도구 번들 | 전문가 페르소나 + 행동 원칙 |
| 위치 | `.claude/skills/` | `.claude/agents/` |
| 트리거 | 사용자 요청 키워드 매칭 | Agent 도구 명시적 호출 |
| 용도 | "어떻게 하는가" | "누가 하는가" |

### 연결 방식

- **Skill 도구 호출**: 스킬이 독립 워크플로우이고 재사용 가능
- **프롬프트 인라인**: 스킬이 짧고(50줄 이하) 에이전트 전용
- **레퍼런스 로드**: 스킬이 크고 조건부로만 필요
