# Harness — Agent Team & Skill Architect

도메인 설명을 입력하면 에이전트 팀과 그들이 사용할 스킬을 자동 생성하는 메타 스킬.

**참고 자료 위치:** `references/` 디렉토리
- `agent-design-patterns.md` — 아키텍처 패턴 및 에이전트 분리 기준
- `orchestrator-template.md` — 오케스트레이터 구현 템플릿 (팀/서브/하이브리드)
- `skill-writing-guide.md` — 스킬 작성 및 재사용 설계
- `skill-testing-guide.md` — 테스트 방법론
- `qa-agent-guide.md` — QA 에이전트 특화 가이드
- `team-examples.md` — 실제 팀 파일 예시

---

## 기본 원칙

- **에이전트 팀을 기본 실행 모드로 사용** — 2명 이상이고 상호 통신이 필요하면 에이전트 팀
- **에이전트는 파일 기반 정의 필수** — `.claude/agents/{name}.md` 형식
- **모든 에이전트는 `model: "opus"` 사용**
- **CLAUDE.md에는 포인터만 등록** — 트리거 규칙 + 변경 이력만, 포괄적 목록 아님
- **하네스는 지속적으로 진화** — 정적 구조물이 아닌 피드백 기반 성장 시스템

## Phase 0: 현황 감사

`_workspace/` 디렉토리 존재 여부로 실행 경로 결정:

| 상태 | 경로 |
|------|------|
| `_workspace/` 없음 | 신규 구축 → Phase 1로 |
| `_workspace/` 있음 + 완료 표시 | 새 실행 (이전 결과 보존) → Phase 1로 |
| `_workspace/` 있음 + 미완료 | 부분 재실행 → 미완료 Phase부터 재개 |

기존 `.claude/agents/`와 `.claude/skills/` 검토 → 충돌/중복 확인:
- 신규 에이전트/스킬과 기존 항목 비교
- 확장 vs 신규 생성 결정

## Phase 1: 도메인 분석

사용자 입력을 분해하여 다음을 정의:

1. **핵심 도메인** — 무엇을 자동화하는가
2. **주요 작업** — 어떤 작업들이 필요한가
3. **작업 간 의존성** — 순차적/병렬적 관계
4. **전문성 분리 기준** — 어떤 역할들이 필요한가
5. **산출물 유형** — 무엇을 생성/처리하는가

`_workspace/01_domain_analysis.md`에 저장.

## Phase 2: 팀 아키텍처 설계

### 실행 모드 선택

```
에이전트가 2명 이상인가?
  ├─ YES: 상호 통신이 필요한가?
  │     ├─ YES → 에이전트 팀 모드 (기본)
  │     └─ NO  → 서브 에이전트 모드 가능
  └─ NO: 단일 에이전트 or 스킬만으로 충분
```

→ `references/agent-design-patterns.md` 참조

### 아키텍처 패턴 선택

| 패턴 | 적합 상황 |
|------|---------|
| **Pipeline** | 순차 작업, 이전 단계 → 다음 단계 |
| **Fan-out/Fan-in** | 병렬 처리 후 통합 |
| **Expert Pool** | 조건에 따라 전문가 선택 호출 |
| **Producer-Reviewer** | 생성-검증 쌍 동작 |
| **Supervisor** | 중앙 에이전트가 동적으로 작업 분배 |
| **Hierarchical Delegation** | 재귀적 위임 (2단계 이내 권장) |

`_workspace/02_architecture.md`에 설계 저장.

## Phase 3: 에이전트 정의 생성

각 에이전트에 대해 `.claude/agents/{name}.md` 생성:

```markdown
---
name: agent-name
description: "1-2문장 역할 설명 — 이 에이전트가 언제 호출되는지 포함"
model: opus
---

# Agent Name

당신은 [도메인]의 [역할] 전문가입니다.

## 핵심 역할
[주요 책임 3-5개]

## 작업 원칙
[의사결정 기준과 이유]

## 입력/출력 프로토콜
- 입력: [무엇을 받는가]
- 출력: [무엇을 생성하는가, 파일 경로 포함]

## 팀 통신 프로토콜 (팀 모드인 경우)
- SendMessage 대상과 내용
- 수신 메시지 처리 방법

## 에러 핸들링
[실패 시 동작]
```

**중복 검토 필수:** 기존 에이전트와 역할이 겹치면 신규 생성 대신 확장.

## Phase 4: 스킬 생성

각 스킬에 대해 `.claude/skills/{name}/SKILL.md` 생성.

→ `references/skill-writing-guide.md` 참조

### 스킬 작성 핵심 원칙

**Description은 트리거 메커니즘이다:**
- 스킬이 하는 일 + 구체적 트리거 상황 모두 기술
- 후속 작업 키워드 반드시 포함 ("재실행", "업데이트", "수정", "보완")
- 약간 "pushy"하게 작성

**본문 작성:**
- Why-First 원칙: 이유를 이해하면 엣지 케이스에서도 올바르게 판단
- SKILL.md는 500줄 이내 유지 — 초과 시 `references/`로 분리
- 스킬은 AI 에이전트를 위한 지시서 (README 아님)

**중복 검토:**

| 상황 | 조치 |
|------|------|
| 기존 스킬이 완전히 포함 | 신규 생성 금지 — 기존 스킬 재사용 |
| 기존 스킬이 부분 포함, 일반화 가능 | 기존 스킬 확장 |
| 도메인 특화 의도된 부분 포함 | 신규 생성 (별개 스킬 유지) |
| 기능 범위 완전히 다름 | 신규 생성 |

## Phase 6: 검증

### 구조 검증
- [ ] 에이전트 파일 생성됨 (기존 중복 검토 완료)
- [ ] `model: "opus"` 모든 에이전트에 명시
- [ ] 스킬 description에 "후속 작업 키워드" 포함
- [ ] SKILL.md 500줄 이내 (초과 시 references/ 분리)
- [ ] CLAUDE.md 포인터 등록

### 트리거 검증
각 스킬의 description에 대해:
- 트리거해야 할 쿼리 10개 테스트
- 트리거하면 안 되는 쿼리 10개 테스트
- 기존 스킬과의 description 충돌 확인

→ `references/skill-testing-guide.md` 참조

### 드라이런
실제 실행 전 각 Phase의 산출물을 검토하여 누락/오류 확인.

## Phase 7: 진화

실행 후 피드백 수집 및 반영:

1. **피드백 수집** — 예상과 다른 동작, 불필요한 단계, 누락된 기능
2. **일반화** — 특정 예시에만 맞는 좁은 수정 대신 원리 수준에서 일반화
3. **반복 번들링** — 매번 반복되는 작업은 스킬 본문에 표준화
4. **변경 이력 기록** — CLAUDE.md에 날짜와 변경 내용 추가

**진화가 하네스의 진짜 가치다** — 첫 실행보다 10번째 실행이 더 좋아야 한다.
