## 구현하지 않은 것들

### 훅 시스템(Hook System)

Claude Code는 25가지 훅 이벤트와 6가지 훅 타입을 가지며, 도구 실행 전후에 커스텀 로직을 삽입할 수 있습니다. 위험한 작업을 차단하고, 감사 로그를 기록하고, 자동으로 lint 검사를 실행합니다. 이것이 Claude Code를 "도구"에서 "플랫폼"으로 변환하는 핵심 메커니즘입니다.

구현하지 않은 이유: 핵심 도전은 "함수 호출"이 아니라 훅 발견 및 로딩, 오류 격리, stdin/stdout JSON 데이터 프로토콜입니다. 이 엔지니어링 세부사항은 약 500-800줄 분량이지만 에이전트 원리 이해에 도움이 되지 않습니다.

### 오케스트레이터/스웜 멀티 에이전트 모드

우리는 서브 에이전트(fork-return)를 구현했습니다. Claude Code에는 두 가지 추가 모드가 있습니다. **오케스트레이터**는 대규모 작업을 분할하여 여러 전문 에이전트에게 맡기고, **스웜**은 여러 에이전트가 동료로서 통신하며 병렬로 탐색합니다. 두 모드 모두 단일 에이전트의 컨텍스트가 충분하지 않을 때의 작업 분해 문제를 해결합니다.

구현하지 않은 이유: 핵심 도전은 작업 분해 정확도와 에이전트 간 통신 프로토콜 설계입니다. 코드 아키텍처 문제보다는 프롬프트 엔지니어링 문제입니다. 구현 자체는 복잡하지 않지만 실제로 유용하게 만들려면 광범위한 프롬프트 튜닝이 필요합니다.

### LSP 통합

LSP는 파일 수정 후 전체 컴파일/테스트 사이클을 기다리지 않고 밀리초 단위의 타입 오류 피드백을 에이전트에게 줍니다. 대규모 프로젝트에서 버그 수정에 필요한 반복 횟수를 30-50% 줄일 수 있습니다.

구현하지 않은 이유: LSP 서버 프로세스 관리, 클라이언트 프로토콜 구현(초기화 핸드셰이크, 기능 협상, 증분 동기화)이 필요합니다. 1000줄 이상이며 LSP 프로토콜에 대한 깊은 이해가 필요합니다. 셸 명령어(`tsc --noEmit`, `python -m py_compile`)를 통해 오류 피드백을 얻는 것으로 튜토리얼 시나리오에 충분합니다.

### 프롬프트 캐싱

Anthropic API는 시스템 프롬프트 캐싱을 지원합니다. Claude Code는 변하지 않는 부분(역할 정의, 도구 스펙)을 앞에, 변하는 부분(git 상태, 현재 파일)을 뒤에 배치합니다. 캐시 히트 시 입력 토큰 비용을 90% 절감할 수 있습니다.

구현하지 않은 이유: 코드 변경은 최소화됩니다(20-30줄). 하지만 프롬프트 분할 전략을 신중하게 설계해야 합니다. 에이전트를 프로덕션에 배포할 계획이라면 가장 먼저 추가해야 할 최적화입니다.

### Bash AST 보안 분석

Claude Code는 tree-sitter를 사용하여 셸 명령어 AST를 파싱하고, 23가지 정적 보안 검사를 수행합니다. 파이프 조합 내의 위험한 명령어를 분석할 수 있는데, 순수 정규식으로는 불가능합니다.

구현하지 않은 이유: tree-sitter는 `node-gyp` 빌드 환경이 필요한 네이티브 C/C++ 라이브러리로 환경 장벽이 너무 높습니다. 정규식 매칭으로 일반적인 위험 패턴의 80%를 커버하며, 튜토리얼 시나리오에서 위험은 허용 가능합니다.

## 점진적 개선 로드맵

### 1단계: 성능 및 비용 최적화 (1-2일)

| 개선사항 | 해결하는 문제 | 예상 코드 |
|---------|------------|---------|
| 프롬프트 캐싱 | 시스템 프롬프트 재전송으로 인한 토큰 낭비 | ~30줄 |

**프롬프트 캐싱**은 투자 대비 최고의 최적화입니다. 시스템 프롬프트의 정적 부분에 `cache_control: { type: "ephemeral" }` 마커를 추가하면 멀티턴 대화에서 입력 토큰 비용을 50% 이상 절약할 수 있습니다.

### 2단계: 확장성 (3-5일)

| 개선사항 | 해결하는 문제 | 예상 코드 |
|---------|------------|---------|
| 훅 시스템 | 에이전트 동작 커스터마이징에 소스 코드 수정 필요 | ~300줄 |
| 도구 타입 시스템 | switch/case가 20개 이상의 도구로 확장되지 않음 | ~200줄 |

핵심 전환은 **하드코딩에서 플러그인 기반으로**입니다. 현재 switch/case는 10개의 도구에서 잘 동작하지만, 20개를 넘어가면 Tool 인터페이스(또는 Python의 Protocol/ABC)를 도입하여 각 도구를 독립 모듈로 만들어야 합니다.

### 3단계: 안정성 및 보안 (1-2주)

| 개선사항 | 해결하는 문제 | 예상 코드 |
|---------|------------|---------|
| 7가지 오류 복구 전략 | 현재 오류 발생 시 충돌 | ~400줄 |
| Bash AST 보안 분석 | 정규식이 복잡한 위험 명령어를 놓침 | ~600줄 |

Claude Code의 `query.ts`는 1728줄이며, 대부분이 엣지 케이스를 처리합니다. Prompt Too Long 시 자동 압축 후 재시도, API 과부하 시 지수 백오프, 도구 실패를 모델에 피드백하여 자가 수복이 가능하도록 합니다.

### 4단계: 고급 에이전트 기능 (2-4주)

| 개선사항 | 해결하는 문제 | 예상 코드 |
|---------|------------|---------|
| 오케스트레이터 모드 | 대규모 작업이 단일 에이전트 컨텍스트 용량을 초과 | ~500줄 |
| 스웜 모드 | 탐색적 작업에 다중 경로 병렬 처리 필요 | ~600줄 |
| LSP 통합 | 타입 오류를 컴파일을 통해서만 발견 가능 | ~1000줄 |

## 확장 방향

### 1. 훅 시스템

가장 단순한 접근법은 명령어 훅입니다. `executeTool` 전에 셸 자식 프로세스를 생성하고, stdin JSON으로 도구 정보를 전달하고, stdout JSON을 파싱하여 허용/거부를 결정합니다.

설정 예시:
```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "run_shell", "command": "./hooks/pre-shell.sh" }
    ]
  }
}
```

핵심 로직: 매칭되는 훅을 순회하고, JSON을 전달하여 자식 프로세스를 생성하고, `{"action": "allow"}` / `{"action": "deny", "reason": "..."}` 기반으로 실행 계속 여부를 결정합니다. 약 300줄이며, 가장 시간이 걸리는 부분은 자식 프로세스 타임아웃과 충돌 처리입니다.

### 2. 오류 자가 수복

도구 실행 오류를 루프를 중단하는 대신 도구 결과로 모델에 피드백합니다. 모델은 종종 자가 수복이 가능합니다. 경로가 잘못되면 다른 경로를 시도하고, 명령어 인수가 잘못되면 인수를 수정합니다.

```typescript
try {
  result = await executeToolImpl(name, input);
} catch (e) {
  result = `Error: ${e.message}\n\nPlease try a different approach.`;
}
// 결과를 tool_result로 모델에 반환
```

약 50-80줄이지만 에이전트의 실제 사용성을 크게 향상시킵니다. 이것이 Claude Code의 가장 스마트한 설계 중 하나입니다.

## 핵심 인사이트

**1. 에이전트는 본질적으로 while 루프다**

```
while true:
    response = llm.call(messages)
    if no tool_calls in response: break
    for tool_call in response.tool_calls:
        result = execute(tool_call)
        messages.append(result)
```

모든 복잡성 — 권한, 컨텍스트 관리, 메모리, 멀티 에이전트 — 은 이 루프를 둘러싼 개선과 보호입니다.

**2. 프롬프트는 가장 저렴한 코드다**

시스템 프롬프트의 한 문장이 if 문과 동일한 효과를 가지며, 구현 비용은 0줄입니다. 에이전트 개발에서 많은 동작 문제의 최적 해결책은 더 많은 코드를 작성하는 것이 아니라 더 나은 프롬프트를 작성하는 것입니다. 더 유연하고, 수정이 쉬우며, 비기술적인 사람도 읽을 수 있습니다.

**3. 도구 설계가 기능 한계를 결정한다**

모델이 잘 하는 것(의도 이해, 코드 생성)은 모델이 하게 하고, 도구가 잘 하는 것(정확한 문자열 매칭, 파일시스템 작업, 프로세스 관리)은 도구가 하게 합니다. `edit_file`이 고전적인 예입니다. 모델이 대체할 내용을 생성하면 도구가 파일에서 정확하게 위치를 찾아 교체합니다.

**4. 컨텍스트 관리는 에이전트의 "메모리"다**

컨텍스트 관리는 에이전트에게 있어 메모리 관리가 운영 체제에게 있는 것과 같습니다. 제한된 자원을 사용하여 "무한"의 환상을 제공합니다. 4단계 압축 파이프라인은 에이전트가 유한한 윈도우 내에서 긴 대화의 메모리를 유지할 수 있게 합니다.

**5. 보안은 후속 조치가 아니다**

권한 검사는 미들웨어로 덧붙여진 것이 아닌 에이전트 루프의 한 단계입니다. 어떤 도구도 이를 우회할 수 없습니다. 더 중요한 것은 fail-closed 설계를 사용한다는 점입니다. 새 도구가 권한 레벨 선언을 잊으면 자동으로 "확인 필요"로 처리됩니다. 시스템이 기본값을 통해 안전을 보장합니다.

**6. 3,000줄에서 500,000줄까지의 격차는 엣지 케이스다**

Claude Code의 추가 코드 대부분은 다음을 처리합니다. 크로스 환경 호환성, 네트워크 및 API 불안정성, 사용자 입력 다양성, 엔터프라이즈 수준의 감사 및 접근 제어. 이 "지루한" 코드는 아키텍처 다이어그램에 나타나지 않지만, 도구가 실제 세계에서 안정적으로 실행될 수 있는지의 핵심입니다. 프로토타입에서 제품까지, 거리의 80%가 여기에 있습니다.

**7. LLM과 코드 간의 협업 경계**

코딩 에이전트를 만드는 데 있어 가장 본질적인 기술: LLM과 코드 사이의 올바른 협업 경계를 설계하는 것입니다. LLM이 결정하는 것과 코드가 결정하는 것은 무엇인가? 경계가 잘 그어지면 에이전트는 유연하면서도 안정적입니다. 이 튜토리얼의 모든 설계 결정이 이 원칙을 반영합니다. 모델이 "무엇을 할지" 결정하고, 코드가 "안전하게 수행되도록" 보장합니다.

## 결론

~4300줄의 코드(TS) / ~3800줄(Python), 12개 파일로 코딩 에이전트의 핵심 컴포넌트와 고급 기능을 커버합니다.

**1단계 — 핵심 컴포넌트:** 에이전트 루프, 도구 시스템 (13개 도구 + mtime 보호 + 지연 로딩 + 병렬 실행), 시스템 프롬프트 (Markdown 템플릿 + @include + 환경 주입), CLI / 세션 (REPL + JSON 영속성), 스트리밍 출력 (Anthropic + OpenAI 이중 백엔드 + 스트리밍 도구 실행), 권한 보안 (5가지 모드 + 선언적 규칙 + 정규식 + 확인), 컨텍스트 관리 (4단계 압축 + 대용량 결과 영속성)

**2단계 — 고급 기능:** 메모리 시스템 (시맨틱 리콜 + 비동기 프리페치), 스킬 시스템 (inline/fork 이중 모드), 플랜 모드 (읽기 전용 계획 수립 + 4가지 옵션 승인), 멀티 에이전트 (서브 에이전트 + 3가지 내장 타입 + 커스텀), MCP 통합 (JSON-RPC over stdio), 예산 제어

Claude Code의 500,000줄 코드 중 대부분은 엣지 케이스 처리와 엔터프라이즈 수준의 안정성입니다. 하지만 핵심 에이전트 기능 — 사용자 의도 이해 -> 도구로 코드 조작 -> 완료될 때까지 반복 — 은 정확히 이 ~3400줄이 하는 것입니다.

이제 기능이 풍부한 코딩 에이전트를 갖게 되었고, 모든 코드 라인 뒤에 있는 설계 의도를 이해하게 되었습니다. 이제 확장하세요.
